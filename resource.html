What this project is
Weave is a peer-to-peer compute network: idle consumer devices (laptops, desktops, eventually phones) contribute spare compute to run jobs — starting with AI inference — and earn credits they can spend on compute themselves. Think BitTorrent's reciprocity model applied to compute instead of files. The wedge use case is AI inference because it's embarrassingly parallel (each job is independent, no tight cross-device synchronization required to start generating revenue). The long-term vision is a general protocol layer for distributed consumer compute — rendering, simulation, eventually training — but the engineering plan below deliberately scopes phase 1–3 to the narrowest viable slice.
The single most important fact before you start
A production-grade open-source project called exo already solves the hardest sub-problem — dynamically partitioning a large model across heterogeneous consumer devices (a MacBook, a gaming PC, a Raspberry Pi) and running inference across them with automatic device discovery. It is local-network only, has no incentive layer, no WAN P2P, and no security model for untrusted third-party contributors. Don't reinvent this layer from scratch. Clone it, run it on two machines in week one, read its source for the partitioning/discovery logic, and build the missing pieces (WAN networking, credits, verification, sandboxing) on top or alongside it. This single decision can save 2-3 months of the build timeline.

Recommended reading order for the agent

1. Run exo locally on two machines first — get hands-on with the core primitive before reading anything else.
2. Read the Petals paper + repo — this is the WAN-scale version of what exo does locally, including the DHT peer-discovery pattern Weave needs.
3. Read MDI-LLM — the cleanest description of activation-passing and shard-assignment between heterogeneous low-power nodes.
4. Read TOPLOC — the verification layer; how to know a contributor actually did the compute correctly.
5. Skim the Precedents tab in full — especially the Golem failure analysis. Every design decision in the Build Pipeline tab traces back to avoiding a specific failure mode documented there.
6. Then proceed to the Tech Stack and Build Pipeline tabs.

Non-negotiable design constraints (derived from precedent failures)

No cryptocurrency, no wallet requirement. Credits are an internal ledger entry, not a token. This is the single biggest factor separating SaladCloud's traction from Golem's decade of failure.

AI inference first, general compute later. Don't build a general-purpose compute marketplace before proving the model on one embarrassingly-parallel, high-demand workload.

Consumer product, not just a technical API. A device client real people install matters as much as the API developers integrate against.

Desktop/laptop only at launch. No mobile promises in phase 1-4. iOS background compute is structurally near-impossible; Android is viable but adds complexity that should come after the core protocol is proven.

Heterogeneous / distributed inference engines — the core technical primitive

exo★ Read first
repoactive
Production-grade open-source project: run your own AI cluster at home with everyday devices. Automatic dynamic model sharding across heterogeneous hardware (Mac via MLX, Linux/Nvidia via tinygrad, even Raspberry Pi), zero-config local network device discovery, ChatGPT-compatible API endpoint. Layers automatically partitioned proportional to each device's memory/compute. Can run 70B+ parameter models across a cluster no single device could handle alone.
What to borrow: the dynamic partitioning/sharding algorithm and the multi-backend execution layer (MLX + tinygrad). What's missing that Weave must build: WAN-scale P2P (it's LAN-only today), an incentive/credit layer, and a security/sandboxing model for untrusted third-party nodes.
github.com/exo-explore/exo
Petals
repopaperactive
"Run LLMs at home, BitTorrent-style." Production system for pipeline-parallel inference and fine-tuning of LLMs over the open internet. Each peer hosts a few transformer blocks; a Kademlia-style DHT handles peer discovery and swarm formation; 8-bit (and 4-bit/NF4) quantization compresses activations passed between peers; built-in load balancing distributes blocks evenly across the swarm. Explicitly documents that hosting a server does not allow others to execute arbitrary code on your machine.
What to borrow: the DHT peer-discovery pattern (this is the WAN equivalent of exo's local discovery), the activation quantization approach for low-bandwidth links, and the security framing for what a "host" can and can't do.
github.com/bigscience-workshop/petals · ACL 2023 System Demonstrations paper
MDI-LLM
paper
"Model-Distributed Inference for Large Language Models at the Edge" (arXiv 2505.18164, May 2025). Introduces "recurrent pipeline parallelism" — partitions a model across low-power edge nodes that exchange intermediate activation vectors over device-to-device links, reducing per-device idle time and enabling parallel inference across multiple concurrent sequences. Validated on 3× Nvidia Jetson TX2 boards (8GB RAM each) over gigabit Ethernet, using TCP/IP sockets for coordination.
What to borrow: the cleanest available description of the layer-to-node assignment problem and the activation-passing protocol between heterogeneous low-power devices — directly informs Weave's shard-assignment algorithm.
arxiv.org/abs/2505.18164 — Macario, Seferoglu, Koyuncu (UIC)
distributed-llama
repoactive
Lightweight C++ implementation of tensor-parallel LLM inference distributed across a home cluster of devices.
What to borrow: a minimal, fast reference implementation of tensor parallelism if exo's Python stack proves too heavy for low-power contributor nodes.
github.com/b4rtaz/distributed-llama
Prima.cpp
paper
"Fast 30-70B LLM Inference on Heterogeneous and Low-Resource Home Clusters" (arXiv 2504.08791). Targets exactly Weave's hardware reality: mixed clusters of phones, Raspberry Pis, laptops. Strong related-work section cataloguing the entire edge-inference ecosystem (llama.cpp, AirLLM, TPI-LLM, MLC-LLM, ktransformers, exo, distributed-llama).
What to borrow: use its references section as a secondary reading list — it's the most complete bibliography of the edge/heterogeneous inference space available.
arxiv.org/abs/2504.08791
TPI-LLM
paper
"Serving 70B-scale LLMs Efficiently on Low-Resource Edge Devices" (arXiv 2410.00531). Tensor-parallel inference approach specifically optimized for memory-constrained edge hardware.
What to borrow: memory-constraint optimization techniques for the lowest tier of contributor devices (older laptops, CPU-only machines).
arxiv.org/abs/2410.00531
llama.cpp / MLC-LLM / ktransformers
repoactive
Single-node inference runtimes, already heavily optimized for consumer hardware (CPU, Apple Silicon, consumer GPU). These are the execution engines that run inside a single Weave shard — no need to write a custom inference kernel.
What to borrow: use one of these as the per-node execution engine within each shard; don't write inference kernels from scratch.
github.com/ggerganov/llama.cpp · github.com/mlc-ai/mlc-llm · github.com/kvcache-ai/ktransformers
B

Video / diffusion-specific distributed inference

Video-Infinity
repopaper
"Distributed Long Video Generation" (arXiv 2406.16260). Introduces Clip Parallelism (splits a long video into clips processed across GPUs with minimal context-sharing overhead) and Dual-Scope Attention (balances local vs global temporal context). Generated 2,300 frames in ~5 minutes on 8× RTX 6000 Ada GPUs — 100x faster than prior methods.
What to borrow: the clip-parallel decomposition strategy — directly relevant when Weave expands into video/rendering workloads in Phase 5.
arxiv.org/abs/2406.16260 · github.com/Yuanshi9815/Video-Infinity
Heterogeneous Decentralized Diffusion Models
paper
arXiv 2603.06741 (Mar 2026). Decentralized training framework allowing diffusion model "experts" to use different objectives (DDPM, Flow Matching), unified at inference via deterministic schedule-aware conversion. Reduces training compute from 1,176 to 72 GPU-days (16x) relative to prior decentralized diffusion training work.
What to borrow: a forward-looking reference for the long-term "federated training" phase (Phase 6) — not relevant to early phases.
arxiv.org/abs/2603.06741
C

Verification & trust for untrusted compute

TOPLOC★ Verification layer
repopaperactive
"A Locality Sensitive Hashing Scheme for Trustless Verifiable Inference" (arXiv 2501.16007, Prime Intellect). Compact LSH mechanism over intermediate activations detects unauthorized model/prompt/precision modifications with 100% accuracy in their empirical evaluation, zero false positives/negatives. 1000x storage reduction vs raw activation storage (258 bytes per 32 tokens vs 262KB). Robust across different GPU types and tensor-parallel configurations. Integrated with vLLM, forked into SGLang.
What to borrow: this is the most directly applicable, production-ready answer to "how do I know a contributor's device actually ran the job correctly without re-running everything myself." Build Weave's verification layer directly on this.
arxiv.org/abs/2501.16007 · github.com/PrimeIntellect-ai/toploc · github.com/PrimeIntellect-ai/toploc-experiments
awesome-sandbox
repoactive
Curated list of code-sandboxing tools for AI/untrusted execution (e2b, microsandbox, and others). WebAssembly's security model is capability-based — a WASM module is inert by default with no filesystem, network, or host-memory access unless explicitly granted, and the runtime bounds-checks every memory access.
What to borrow: reference list for evaluating sandbox runtimes when Phase 2 introduces untrusted third-party contributor nodes.
github.com/restyler/awesome-sandbox
D

Coordination & task scheduling

Ray
repoactive
Distributed task-graph execution framework from UC Berkeley (RISELab). The task graph is constructed dynamically as the application runs — not a fixed DAG defined upfront — which fits a job-routing coordinator better than batch schedulers like Slurm.
What to borrow: use as the coordinator's task scheduling substrate rather than building a custom scheduler from scratch.
github.com/ray-project/ray · bair.berkeley.edu/blog/2018/01/09/ray
Matrix (P2P Multi-Agent Synthetic Data Generation)
paper
arXiv 2511.21686. Peer-to-peer framework where each task progresses independently through lightweight agents while compute-intensive operations (LLM inference, containerized environments) are handled by distributed services. Built on Ray; scales to tens of thousands of concurrent agentic workflows.
What to borrow: the architectural pattern of separating lightweight coordination logic from heavy compute execution — directly informs the coordinator/worker split in Weave's design.
arxiv.org/abs/2511.21686
CollaPipe
paper
"Adaptive Segment-Optimized Pipeline Parallelism for Collaborative LLM Training in Heterogeneous Edge Networks" (arXiv 2509.19855). Jointly optimizes model segment allocation, micro-batch size, bandwidth, and transmission power for mobile-edge pipeline-parallel training.
What to borrow: the joint-optimization formulation (segments × bandwidth × power) — relevant once Weave's scheduler needs to optimize across more than just compute capability.
arxiv.org/abs/2509.19855
Prime Intellect Protocol
repoactive
Reference implementation (Rust) of a P2P compute protocol with workers, validators, and an orchestration layer. Powered Prime Intellect's distributed training runs (INTELLECT-2, SYNTHETIC-2).
What to borrow: the workers/validators/orchestrator separation of concerns as a reference architecture, even though Prime Intellect targets datacenter-grade nodes rather than consumer devices.
github.com/PrimeIntellect-ai/protocol
E

P2P networking infrastructure

libp2p
repoactive
Modular P2P networking stack originally built for IPFS, now used across the decentralized-systems ecosystem. Provides transport-agnostic dialing/listening, peer discovery, peer routing, content routing, GossipSub pub/sub messaging, and built-in NAT traversal (relay + hole punching). No need to pre-assign ports — peers discover each other dynamically.
What to borrow: use directly as Weave's WAN networking layer — this is the production-grade equivalent of writing your own peer discovery and NAT traversal code, which you should not do from scratch.
docs.libp2p.io · docs.ipfs.tech/concepts/libp2p
IPFS
repoactive
Content-addressed, P2P distributed file system. Relevant if/when model weight distribution itself should be peer-to-peer (so contributor nodes don't all redundantly download multi-gigabyte model weights from Hugging Face Hub).
What to borrow: defer until Phase 4+; relevant once the contributor base is large enough that P2P weight distribution saves meaningful bandwidth cost vs a CDN.
docs.ipfs.tech
F

Volunteer computing precedent infrastructure

BOINC
repoactive
Berkeley Open Infrastructure for Network Computing. 20+ years in continuous production (originated from SETI@home), client-server volunteer-compute middleware, supports dozens of independent scientific projects, built-in credit system for contribution tracking.
What to borrow: not the architecture (client-server, not true P2P) but the operational reliability patterns — work unit checkpointing, resumable jobs, and the credit-accounting approach for tracking volunteer contribution over years of uptime.
github.com/BOINC/boinc · boinc.berkeley.edu

The Golem post-mortem — read before designing anything

Golem is the most important cautionary precedent in this space: ten years of development, $8.6M raised at ICO, 82% of token supply distributed to the community, and zero protocol revenue. Development on the core yagna repo shows no commits since October 2025. Four specific, identifiable causes, each directly actionable as a design constraint:

1. Crypto-first UX — required a GLM token and a crypto wallet before a user could do anything. → Weave uses an internal credit ledger, no wallet, no token.
2. No killer use case — general-purpose CGI rendering for a niche artist community never reached critical mass. → Weave leads with AI inference, a proven, high-demand, easy-to-price workload.
3. Technical API, not a consumer product — Golem was built for developers integrating an API, with no consumer-facing app that made contribution easy or rewarding. → Weave ships a real device client with a real onboarding flow from day one.
4. No mobile path, ever — desktop-only for its entire lifetime, missing the majority of idle compute that exists on phones. → Weave designs for an eventual Android path even though it launches desktop-only.

Build-vs-borrow decision summary

Borrow (don't rebuild): P2P networking (libp2p), local model partitioning logic (study exo's approach), single-node inference execution (llama.cpp/MLX/tinygrad), task scheduling substrate (Ray), verification primitive (TOPLOC).

Build custom (the actual product): WAN-scale extension of exo's partitioning to untrusted internet peers, the credit ledger and incentive economics, the contributor onboarding/device-client UX, the developer-facing API and billing layer, the security/sandboxing wrapper around untrusted job execution, and the coordinator logic that ties scheduling + verification + payment together into one coherent job lifecycle.

Full pipeline — phase by phase, week 1 through 18 months+

PHASE 0
Foundation & Validation
Week 1–2
Goal: get hands-on with the existing closest solution before designing anything, and make the one architectural decision that determines the rest of the timeline — build on exo or build from scratch.
Tasks
  • Clone and run exo across two real machines (e.g. a MacBook + a Linux desktop). Get a 7-13B model running split across both.
  • Read the Petals paper + skim its source for the DHT peer-discovery implementation.
  • Read MDI-LLM and TOPLOC in full — these two papers most directly inform Phase 1-2 design.
  • Make and document the build-vs-fork decision for the partitioning engine (recommended: fork/extend exo's core, don't rewrite it).
  • Stand up repo structure, CI pipeline, and basic structured logging/telemetry from day one.
  • Define the single MVP workload precisely: one model (e.g. Llama-3.1-8B-Instruct or Mistral-7B), one task type (batch text generation, not interactive chat).
Success criteria
  • exo runs successfully across 2 heterogeneous machines on your own network.
  • Written 1-page architecture decision record: fork exo vs build custom, with rationale.
  • Repo scaffolded with CI, the MVP model/workload chosen and documented.
Primary references: exo-explore/exo, bigscience-workshop/petals, arXiv 2505.18164, arXiv 2501.16007
PHASE 1
Two-Node WAN Proof of Concept
Week 3–8 (~Day 60)
Goal: prove the core primitive works over the open internet between two devices you don't physically control together — not just on a LAN.
Tasks
  • Extend exo's local partitioning logic to communicate over a libp2p transport instead of local network discovery — handle NAT traversal via libp2p relay/hole-punching.
  • Build a minimal coordinator service: job intake → node availability check → shard assignment → result return.
  • Implement a basic credit ledger (Postgres, double-entry, no blockchain) tracking compute-seconds contributed and consumed.
  • Run the two-node pipeline on physically separate networks (e.g. your laptop on home WiFi + a cloud VM, or two friends' machines in different cities).
  • Benchmark latency and throughput against SaladCloud and a standard cloud inference API (Replicate or similar) as baselines.
  • Container/process isolation for job execution — full untrusted-party sandboxing isn't required yet since you control both nodes, but build the interface so Phase 2 can slot in real sandboxing.
Success criteria
  • A text generation job completes successfully end-to-end across two devices on different physical networks.
  • Credit ledger correctly debits/credits both sides of a job.
  • Latency and cost benchmarks logged and compared against SaladCloud/cloud API baselines.
  • Architecture supports adding a third node without a rewrite.
Primary references: docs.libp2p.io, bigscience-workshop/petals (DHT pattern), arXiv 2505.18164 (activation-passing protocol)
PHASE 2
Heterogeneous Alpha — 5–10 nodes
Day 60–120 (Month 2–4)
Goal: handle real heterogeneity and real failure — different hardware capabilities, nodes dropping mid-job, and the first untrusted (non-founder-controlled) contributor.
Tasks
  • Build device capability profiling (CPU TFLOPS, RAM, GPU VRAM if present, bandwidth) reported at node registration.
  • Implement adaptive shard assignment proportional to device capability — directly modeled on MDI-LLM's layer-to-node assignment approach.
  • Fault tolerance: detect a dropped node mid-job and re-route to another available peer holding the same shard, or restart the job on a fresh allocation.
  • Verification v1: implement TOPLOC-style spot-check hashing on a sample of completed jobs to detect incorrect/tampered compute.
  • Add real sandboxing (WASM or microVM, per the Tech Stack tab) — this phase is the first time a node you don't personally control runs a real job.
  • Build a minimal web dashboard: node status, job queue depth, credit balances.
Success criteria
  • 5–10 nodes across at least 3 distinct hardware profiles (CPU-only laptop, consumer GPU desktop, cloud VM reference node) successfully complete jobs.
  • A simulated node-drop mid-job is correctly detected and the job recovers without manual intervention.
  • TOPLOC-style verification flags at least one deliberately-injected incorrect result in testing.
  • At least one node operated by someone other than the founder(s) completes real jobs inside the sandbox.
Primary references: arXiv 2505.18164, PrimeIntellect-ai/toploc, restyler/awesome-sandbox
PHASE 3
Closed Developer Beta
Month 4–6
Goal: ship a real product surface — something a developer can integrate against and something a contributor can install and trust.
Tasks
  • Public-facing API: Docker container job submission over REST, modeled on Replicate/Modal's developer experience.
  • Python SDK first, JavaScript SDK second.
  • Contributor desktop client with a real installer: macOS, Windows, Linux. Idle-detection logic (screen off + charging/plugged in + on WiFi, configurable).
  • Credit purchase flow (Stripe) for users who want compute without contributing hardware.
  • Expand model support to 2–3 models spanning text and image generation.
  • Security hardening pass: rate limiting, abuse detection, formalize the sandbox escape-prevention testing.
Success criteria
  • 50–100 contributor nodes onboarded through the real installer (not founder-seeded test machines).
  • 20–50 paying developer accounts actively submitting jobs through the API.
  • Zero security incidents during the closed beta window; sandbox escape testing documented and passed.
  • Median job latency and cost benchmarked publicly against SaladCloud and a major cloud API.
Primary references: Replicate/Modal API design patterns, salad.com developer docs (study as a developer account holder)
PHASE 4
Public Beta & Scale
Month 6–9
Goal: open the doors and prove the network scales past the founder's social graph.
Tasks
  • Open public contributor sign-up (remove invite-gate from Phase 3).
  • Add a node reputation/scoring system: uptime reliability × verification accuracy, feeding into job-routing priority.
  • Geographic-aware routing — co-locate shards regionally to reduce cross-device latency.
  • Expand workload types: introduce frame-parallel rendering as the second product vertical (per Video-Infinity's clip-parallel pattern).
  • Begin formal SOC2-track security practices given the larger, fully public attack surface.
  • Consider P2P weight distribution (IPFS) once redundant per-node model downloads become a meaningful bandwidth cost.
Success criteria
  • 500–1,000 contributor nodes active.
  • Defined monthly revenue target hit (set based on Phase 3 actuals × growth assumption).
  • Reputation system measurably improves job success rate vs Phase 2 baseline.
  • Second workload vertical (rendering) live for at least a subset of beta users.
Primary references: arXiv 2406.16260 (Video-Infinity, for the rendering vertical), Render Network as a market-validation precedent
PHASE 5
Platform Expansion
Month 9–18
Goal: move from "AI inference network" to "general distributed compute protocol with multiple live verticals".
Tasks
  • Pipeline-parallel large-model serving (30-70B+) using the exo/Petals/MDI-LLM heterogeneous partitioning approach, now proven at WAN scale.
  • Android contributor path (idle compute via background service, respecting battery/thermal constraints — iOS deliberately deferred or skipped per the Risks tab).
  • Developer ecosystem: a marketplace of pre-built job templates beyond raw model inference.
  • Scientific compute / simulation vertical exploration, following the BOINC precedent for workload types that fit the embarrassingly-parallel constraint.
Success criteria
  • A 30B+ model served successfully across a heterogeneous WAN swarm with acceptable latency for batch use cases.
  • Android client live in at least a limited beta.
  • Thousands of active nodes; revenue and growth metrics positioned for a Series A conversation.
Primary references: all of Tab "Research & Repos" Section A, BOINC's multi-project model
PHASE 6
Long-Term Protocol Vision
18 months+
Goal: the hardest, longest-horizon capabilities — only pursue once the core network is proven, profitable, and resilient.
Tasks
  • Federated/distributed training experiments — gradient communication across consumer nodes (significantly harder than inference; reference: Heterogeneous Decentralized Diffusion Models, arXiv 2603.06741).
  • Progressive decentralization of the coordinator itself, reducing the network's reliance on a single centralized scheduling service.
  • Multi-region redundancy for the coordination layer.
  • Revisit iOS feasibility as Apple's on-device ML/background execution frameworks evolve.
Success criteria
  • A defined, scoped training experiment (not full frontier-scale training) completes successfully across the distributed network.
  • Coordinator decentralization reduces single-point-of-failure risk, measured by network uptime during a coordinator outage drill.
Primary references: arXiv 2603.06741, arXiv 2509.19855 (CollaPipe)

Engineering risks to track throughout the build — not a one-time read

High

iOS background compute is structurally near-impossible

Apple's Background App Refresh is throttled, user-disableable, and not designed for sustained compute workloads. Design the contributor base around desktop/laptop + eventual Android; do not plan for meaningful iPhone participation in any phase below 18 months, and even then treat it as exploratory.

High

One security incident with untrusted code execution is reputationally fatal

Running containerized AI workloads on consumer devices contributed by strangers creates real attack surface — data leakage between jobs, container/sandbox escape, malicious job payloads. The sandboxing investment in Phase 2 must be genuinely solid before any node outside founder control runs a real job, not retrofitted after an incident.

Medium

Verification for non-deterministic/stochastic workloads remains research-stage

TOPLOC handles deterministic-leaning verification well; fully verifying stochastic generation (sampling-based image/video output) is harder. Prime Intellect's TOPLOC v2 (reproducible Gumbel noise sampling) is in progress but not fully published as of this writing — track its release, don't assume it's solved yet.

Medium

Pipeline-parallel reliability compounds multiplicatively

If a job requires N devices online simultaneously and each has uptime probability p, job success probability is p^N. At 90% per-device uptime, a 3-device pipeline succeeds ~73% of the time; a 5-device pipeline ~59%. Favor single-node batch jobs at launch (Phase 1-3); only introduce true multi-device pipeline-parallel serving (Phase 5) once fault-tolerant re-routing (Phase 2) is mature.

Medium

NAT traversal failure rate on real consumer ISPs / CGNAT

A meaningful fraction of consumer connections sit behind carrier-grade NAT where direct P2P hole-punching fails. libp2p's relay fallback handles this but adds latency and routes traffic through relay infrastructure you'll need to provision and pay for. Budget for this in Phase 1 benchmarking, not as a later surprise.

Design

The Golem-pattern avoidance checklist — revisit at every major design decision

No crypto wallet requirement, ever. Real, proven use case before generalizing. Ship a consumer product alongside the API, not instead of it. Keep a credible mobile path on the roadmap even while launching desktop-only. Any design proposal that violates one of these four should be treated as a red flag requiring explicit justification.

Design

Build-vs-borrow discipline

The temptation to rewrite exo's partitioning logic, libp2p's networking, or TOPLOC's verification scheme from scratch "to understand it better" or "to fit our exact needs" should be resisted by default. Time spent reimplementing solved problems is time not spent on the actual differentiators: the incentive layer, the consumer product, and the trust/security model for a genuinely open contributor network.
